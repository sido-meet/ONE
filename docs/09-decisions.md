## 对参考方案的修订

不采用“Rust 微内核 + Wasm 一切”的起步方式。保留 AI 能力优先、对话优先、模块可组合，但不把权限执行和密钥边界交给普通插件替换。

契约在初始化即建立，与 UI 并行演化，不等 0.2 再补。数据恢复排在真实 Agent 之前。浏览器用于快速开发，Tauri 壳从项目开始就准备；桌面实机验收在环境齐全后进行。阶段编号以本仓库路线为准，替代旧聊天中的阶段编号。

## ADR-013：本体与客户端分离

**日期**：2026-10（0.2.0-dev）　**状态**：接受

**问题**：0.1 让主 WebView 持有唯一的 MockClient，pet 与 bubble 窗口向它发命令（见旧版 03 的过渡方案）。这套做法让“桌面端”和“宠物”绑成一个程序：任何一个窗口是宿主，关掉它其余就失效；而“本体只装宠物，桌面端是可选项”这件事在架构上根本无法表达。

**选择**：ONE 本体（core）成为独立进程，持有唯一的 OneClient、权威快照、客户端名册与安装清单。宠物、桌面端、命令行都是对等的客户端：连接、声明能力、收状态。它们之间没有父子关系；需要互相做事时，请求经由本体转发（`capability.call` / `capability.result`），目标由能力名寻址，不由种类硬编码。

**备选**：

- 维持主窗口持有状态：省一个进程，但“默认只装宠物、桌面端可选”无法成立。
- 客户端各自持有运行时：彼此看起来同步，实际各说各话，是最坏的一种假象。
- 进程内 sidecar + stdio：单客户端可行，多客户端是 1 对 1，不满足“本体同时服务多个呈现形式”。

**代价（已接受）**：多一个常驻进程；打包要带上 Node 或编译产物（R02 仍未解决）；开发时要多跑一个终端。壳必须保证本体活着，因此客户端启动时会拉起它，并每 700ms 重试连接。

**验证证据**：`cargo test` 10 项（含定位算法与帧边界）、`pnpm test` 34 项（含握手、协议版本拒绝、跨客户端单 Run 约束、能力转发、断开清理、未连接不显示假数据）、CLI 实测名册与错误、命名管道互通探针。

**迁移影响**：`src/lib/` 的 host/proxy 窗口协议整体退役，改为 core-link + 本体；`tauri.conf.json` 不再声明窗口，窗口由客户端种类动态创建。

**重新评估条件**：R02 打包方案确定后重评进程模型；若本体需要跨机器访问，传输层需换成带鉴权的方案（ADR-014）。

## ADR-016：领域服务是本体外的提供方

**日期**：2026-10（0.2.0-dev）　**状态**：接受（D01 已落地并有行为测试；D02 协议与 D03 独立进程提供方未开始）

**范围**：先只做本机。本体是唯一入口，宠物、桌面端、命令行与将来的 Agent 运行时都经本体取数据。跨机器访问不在本轮 —— 它要给本体加带鉴权的网络服务（端口、TLS、凭据、跨机权限），安全面和工期都另算。**但插件契约按“不排斥远程”来写**：端口只描述数据与行为，不泄漏管道、文件名或本机路径，这样日后加传输不动契约。

**问题**：日历、笔记这类领域能力今天长在 `OneClient` 上（`packages/contracts/src/index.ts:88` 起），和会话运行时 `createConversation / sendMessage / cancelRun` 焊在同一个接口里，`Snapshot` 还带着 `notes` 与 `calendarEvents`。后果是：换一个日历实现就等于换一个 `OneClient`，也就是把会话状态机一起换掉。“可插拔”在这套结构里不成立。

同时领域服务与 Agent 是两类东西：领域服务实现同一套契约、可以有多个实现（本地、Outlook、Google）；Agent 是执行者，走 AgentBinding 映射会话，需要的是接力摘要而不是能力调用。把两者塞进同一个枚举会重演今天的问题。

**选择**：

1. **本体是领域能力的唯一调用方**。宠物、桌面端、命令行、将来的 Agent 运行时，全都经本体调同一个端口；不允许某一方绕过本体自己接一份日历实现。
2. **提供方是本体外的独立进程，像插件一样安装**。本体持有安装清单，负责启动、停止与重连；提供方不自带会话、不自带权限体系。提供方还要自带一份页面（HTML），但那部分不归本条决策管 —— 见 ADR-018，页面在沙箱里渲染，宿主负责容器与权限裁决。
3. **接口规范化**：本体侧定义端口（`CalendarProvider` / `NotesProvider`），实现可以是进程内模块，也可以是管道另一端的远端提供方 —— 本体只认接口，不关心实现在哪。这是“非常依赖本体”的落点：提供方省掉会话、权限、审计和密钥边界，这些一律留在本体与可信主机侧。
4. **输入在本体边界校验一次**。端口签名收 `CalendarCreateInput` 这类已解析类型，不再是 `unknown`；`domain.ts` 里那批 `parseXxx` 就是唯一的校验点。
5. **提供方声明权限，本体裁决**。提供方自报的权利一律忽略（沿用 `CommandContext` 上那条注释的原则）。密钥只进可信主机边界，不进提供方的环境变量。
6. **数据归属提供方**。ONE 只保存引用与来源（`sourceConversationId`），不做二次存储。

**备选**：

- 领域服务留在本体进程内：省一个进程，但换实现要改本体代码，且本体崩溃会带走日历数据。
- 提供方各自带会话与权限：等于把 ADR-013 拆了，多个会话真相。
- 用 MCP 统一所有外部能力：MCP 适合**适配**已有服务，不适合定义本项目自己的会话与权限语义；边界仍需本体这层。

**四条必须现在定死的语义**：

| 情况         | 错误码                             | 本体给出的文案方向                     |
| ------------ | ---------------------------------- | -------------------------------------- |
| 装了但没运行 | `UNAVAILABLE`                      | 说的是“日历源没连上”，不是“功能不存在” |
| 根本没安装   | `UNAVAILABLE` + `details.provider` | “还没有接日历源”，附带怎么装           |
| 装了但没授权 | `PERMISSION_DENIED`                | 明确指出缺哪一项权限                   |
| 版本对不上   | `CONFLICT`                         | 带上双方版本，UI 做对比而不是覆盖      |

`PERMISSION_DENIED` 目前不在 `ErrorCode` 里（`errors.ts:2` 写着“等真有适配器能抛它时再加”）—— 第一个真日历源就是那个时刻，届时要放出来。没有它，“没授权”和“没装”会撞成同一句失败。

**代价（已接受）**：每个提供方一个进程，需要进程监督（ADR-015 的重新评估条件因此提前命中）；规范接口意味着实现方要跟协议演进；本体要为每个提供方写一份远程代理实现。收益是本体崩溃不带走日历数据，且替换实现不用碰本体。

**验证证据**：`packages/provider-local` 是第一个真实实现 —— 本体外的独立进程，数据落自己的目录，经本体转发。实机验收：本体与提供方全部杀掉后重启，日程仍在（同一 id 与标题），幂等键重发返回同一条；杀提供方得 `not-running`（「日历源没有连上」），安装清单里去掉日历源得 `not-installed`（「还没有接日历源」），两者由 `details.providerProblem.reason` 分开。测试：`provider.test.ts` 6 项（落盘、重启后读取、幂等回执也落盘、版本冲突、工作区隔离、坏文件拒绝覆盖）、`registry.test.ts` 7 项（状态现读、断线回落、少报能力算没授权、未登记按没安装、呈现形式冒充 provider 不算数、本体不留实体只转发）、`provider-errors.test.ts` 6 项（未授权与版本冲突的线上回传）。`pnpm test` 69 项全过。

**迁移影响**：`OneClient` 拆成会话运行时与领域端口两部分；`Snapshot` 摘掉 `notes` / `calendarEvents`，改由本体向提供方取；`core.ts` 的命令白名单不再直接转给 `OneClient`，而是先解析到提供方。

**重新评估条件**：出现第二种传输（跨机器）或真正的第三方插件生态时重评；届时权限与签名模型需要整体重写。

## ADR-017：协议拆开角色、寻址与可启动性

**日期**：2026-10（0.2.0-dev）　**状态**：接受（D02 已落地，12 项协议回归测试）

**问题**：ADR-016 要求提供方能注册、能被寻址。但 `wire.ts:15` 原来写的是

```ts
export type ClientKind = 'pet' | 'desktop' | 'cli';
```

这一个字段同时承担三件事，并且出现在 `hello.kind`、`capability.call.target`、`clients.launch.kind`、名册 `clients[].kind`、`installed[]` 五个位置。任何日历提供方来握手，`parseClientMessage` 会当非法帧拒掉 —— 协议层面就不允许第三方存在（`wire.ts:93`、`120`、`124`、`167`、`228`）。

第二个问题是能力名带实现前缀：现有 `pet.bubble.open` 直接认死了“宠物”。日历若照抄成 `calendar.local.create`，换实现就得改调用方代码。

**选择**：

1. 拆成三个正交字段：
   - `role: string` —— 纯标签（`pet` / `desktop` / `cli` / `provider`），本体不为它写任何特判。
   - `provider: string` —— 唯一寻址键（`local.calendar`、`outlook.calendar`），`capability.call.target` 靠它。
   - 安装与可启动性继续由本体的 `installed` 清单掌管，不混进前两个。
2. **能力名只说做什么**：形如 `calendar.create`、`notes.list`，不带实现前缀；提供方是谁由 `target` 决定。
3. 传输不变（ADR-014 的命名管道 + 逐行 JSON），只升 `WIRE_VERSION`。本体对老版本客户端明确拒绝，不做兼容猜测。本轮只跑本机（ADR-016 的范围），但协议里不出现“本机唯一”的假设：注册与寻址不写死传输来源，日后换网络传输时插件契约不用重写。
4. 名册从“客户端”扩成“参与者”：呈现形式与提供方都能查，但**不要让界面把提供方画成宠物** —— 两者的图标和可用操作不同。

**备选**：

- 继续用 `ClientKind` 枚举、每加一种提供方改一次协议：把注册表变成硬编码清单，和 ADR-013/015 冲突。
- 另开一套“插件协议”：两套管道两套握手，装了插件的机器和没装的机器行为不一致。

**代价（已接受）**：一次性协议不兼容，所有客户端必须同版本；`installed` 与 `connected` 的语义要重新界定清楚（连上 ≠ 装了，ADR-015 已确立）。能力名去掉前缀后，短期会有一批调用点要改。

**为什么必须现在定**：能力名和寻址方式是全链路的，越晚改，调用点越多。拖到有第二个提供方之后再改，会同时动协议、本体、壳和前端四层。

**验证证据**：`core/src/wire-v2.test.ts` 12 项。关键几条是旧协议做不到的：日历提供方以 `role=provider, provider=local.calendar` 握手并进入名册；两个 `role` 相同但 `provider` 不同的提供方互不顶掉；同名能力（`window.show`）在宠物与日历之间各投各的；v1 的 hello 连解析层都过不去；寻址键拒绝空格、斜杠与大写 —— 它会进日志、进命令行、进 `one-plugin://` 的 host 部分。Rust 侧 12 项单测，其中 `capability_names_carry_no_implementation_prefix` 把能力名字面量写死，与 TS 侧 `CAPABILITY` 互为对照，改错一边就会红。

**迁移影响**：`WIRE_VERSION` 1 → 2；`packages/contracts/src/wire.ts` 的解析与守卫；`core/src/core.ts` 的会话与名册；壳与前端同步升级。**后续：2 → 3**（ADR-018 落地）—— 参与者多申报一个 `view`（自带页面入口），并新增 `page.read` 帧。之所以再升一次版本而不是加可选字段：v2 的本体会静默丢掉 `view`，于是页面永远打不开而没有任何一方报错。

**重新评估条件**：若最终确定提供方只在本机安装，枚举可以接受 —— 但还差一条：本机的提供方**数量和实现并不固定**（本地文件、Outlook、Google 都可能只装其中一两个），枚举每加一种就要改协议。所以这条不因“只本机”而成立，它要求的是“种类可穷举”，而 ADR-016 要求的是“实现可替换”。

## ADR-018：插件自带页面，宿主提供窗口容器与权限裁决

**日期**：2026-10（0.2.0-dev）　**状态**：接受（代码已落地，见路线 D04/D05/D06）

**问题**：日历、记事本做成插件之后，宠物上方要能悬浮出摘要、点开看内容，宠物提供窗口去打开插件的页面。这逼出一个岔路口：**那块界面是插件画的，还是宿主画的？**

**选择**：插件是**两件货**——一份可被本体调用的数据接口，和一份自带 HTML 视图。数据经本体调用（ADR-016），视图在沙箱 iframe 里渲染，宿主负责窗口容器、布局、权限裁决与数据桥接。宠物是宿主，不是插件。

### 沙箱边界（这条最容易做错）

1. **iframe 的 `sandbox` 只给 `allow-scripts`，绝不给 `allow-same-origin`**。给了 same-origin，插件页面就与宿主同源，能读父页面 DOM、能拿宿主上下文，隔离等于没做。页面因此运行在一个不透明来源（opaque origin）里。
2. **页面没有 Node、没有文件系统、没有网络**。它唯一的出口是 `postMessage` 给宿主；宿主转发到本体，由本体裁决后才回数据。密钥因此留在可信主机边界，插件页面碰不到 —— 这是「密钥不放任意插件」得以成立的原因。
3. **一个插件页面对应一个窗口，窗口与 provider 一一绑定**。宿主不能在消息里相信页面自报的身份：若一个窗口同时加载多个插件页面，或允许页面自称 provider，A 插件就能读到 B 插件的数据。绑定到窗口后，宿主天然知道这个窗口属于谁，页面无从冒充。
4. **宿主转发前必须确认消息来自自己那个 iframe**，`event.origin` 不可信（不透明来源下会是 `null`），要靠 iframe 自身的句柄而不是页面报的身份来路由。

### 页面从哪来

`one-plugin://<provider>/...`，由壳注册自定义协议，按 provider 转交给对应插件进程响应资源请求。不用 localhost HTTP 服务 —— 否则本体要管端口分配、冲突与插件崩溃后的回收，那是一整套独立的问题。插件进程崩了，页面加载失败，宿主显示明确错误，绝不留白屏。

当前 CSP 是 `default-src 'self'`，`frame-src` 会回落到它，会直接挡住 `one-plugin:`，实现时必须一并放开。

**实现时修正一处**：主机名用 `localhost` 而不是 `<provider>`，即 `one-plugin://localhost/local.calendar/calendar.html`。Windows 的 WebView2 不认非标准协议，wry 会先把地址改写成 `http://one-plugin.localhost/...` 再拦截（`custom_protocol_workaround`），寻址键放主机名会在这一步被改坏。寻址键因此放路径里。

**实机再修正一处**：iframe 里要写的**不是** `one-plugin://` 原地址，而是改写后的 `http://one-plugin.localhost/...`。wry 的拦截只匹配那个前缀，而 iframe 走的是资源请求，写原地址压根到不了协议处理器 —— 表现是窗口开着、标题正确、内容一片空白。这个前缀是宿主的事，所以由壳通过 `client_identity` 的 `pluginPageBase` 告诉界面，而不是界面自己猜平台。

**实现时补上第 5 条边界**：`sandbox` 属性挡得住 DOM 访问，挡不住页面自己发起网络请求。因此**插件页面自己的响应带一条 CSP**：`default-src 'none'`，`script-src`/`style-src` 只放行内联，`frame-ancestors` 只认宿主自己的两种来源。代价是插件页面必须是自包含单文件 —— 这是有意的，让插件作者不用再学一套打包。

### 宠物上方那条常驻摘要

分工是：**宿主管「插件在不在」，插件管「自己的内容长什么样」。** 没装或没运行时插件自己不可能画任何东西，这时由宿主画占位并在宠物右键菜单保留入口；插件正常时，摘要条的内容由插件的视图给。这不是把界面收回 ONE，而是把「在场判断」留在唯一知道装了什么的宿主手里。

> **D05 修正（见 ADR-019）**：上面「摘要条的内容由插件的视图给」在**常驻位**上不成立 —— 插件不在场时它连一个字都画不出来，而那正是常驻位最需要它的时候。成立的分工是：**摘要条由宿主给，摘要条点开的那个页面由插件给**。理由与实机证据见 ADR-019。

**常驻位最容易造假，所以三态必须分开说**：

- 没安装 —— 摘要条整体不出现，但宠物右键菜单里的入口要在，点了明确说「还没接日历源」，不是点了没反应；
- 装了没运行 —— 显示「日历源没连上」，**不拿上次缓存的旧日程冒充今天**；
- 装了但没授权 —— 点开说明缺哪一项权限（ADR-016 的 `PERMISSION_DENIED`）。

领域数据不进 `Snapshot`（承接 ADR-016）：摘要条要刷新，挂进会话快照就成了每次广播全量日历。改为独立读命令 + `revision`；面板打开时拉详情，摘要只拉聚合结果。

**备选**：

- 宿主统一渲染、插件只给数据：体验最一致，但日历要画时间轴网格、笔记要长文本编辑，ONE 得为每类能力写一套界面，且插件作者失去表达自由。
- 每个插件开独立 webview 加载：隔离更强，但插件窗口与宠物窗口的布局协调、拖动跟随、层级管理都要重做一轮，代价高于收益。

**代价（已接受）**：**体验会分裂** —— 换 Outlook 实现之后日历长得不一样，因为界面归插件。这是「插件自带页面」的固有代价，不是缺陷，选它就要认。换来的是插件作者有完整表达自由，宿主不必为每类领域能力写界面。宿主另需维护协议桥、自定义协议路由与崩溃兜底。

**为什么必须现在定**：插件作者会按「我的页面长什么样」来设计。按错的假设写出去，之后回改要动所有插件。

**验证证据**：`core/src/page-read.test.ts`（8 项，覆盖「没申报页面 / 没提供 page.read / 没在运行 / 答不上来 / 错误码一路传到界面」五种拒绝路径）、`src/lib/page-bridge.test.ts`（9 项，含「只认自己那个 iframe」与能力表与领域能力一一对应）、`packages/provider-local/src/pages.test.ts`（5 项，含目录穿越、跨身份串页与「页面不引用外部资源」）、`src-tauri/src/plugin.rs`（9 项，含寻址键守卫、窗口标签可逆编码、CSP 字面量、状态码分流）。实机验收记录在 `docs/06-roadmap.md` 的 D04 小节：页面在沙箱 iframe 里真的渲染出来，并列出已落盘的数据。

**D04 实机抓到的六个问题**（都修了，且都补了回归测试）：

1. **一个身份能读到另一个身份的页面**：两个身份共用一个 `pages` 根，向 `local.notes` 要 `calendar.html` 会把日历页面原样端出来。改成按身份分目录，分目录是边界不是整理。
2. **提供方的错误码在管道上丢了**：`capability.result` 的失败帧只带一句话，本体只能按 INTERNAL 处理，于是「没有这个文件」到壳那里变成 502。现在失败帧带 `code`，一路传到 HTTP 状态码。
3. **Tauri 不接受带 `.` 的窗口标签**：`plugin-local.calendar` 直接建不出窗口。标签改成可逆编码（`.`→`_`、`-`→`--`），保证不撞车。
4. **新窗口被 ACL 挡在门外**：`capabilities/default.json` 按窗口标签授权，漏了 `plugin-*`，新窗口里 `plugin:event|listen` 直接被拒，界面停在「启动失败」。
5. **一根管道只有一次握手**，而每个窗口都在握手：本体只认第一次，后开的窗口永远停在「正在连接」（对话条其实一直有这个问题，只是没人注意）。改成只有主窗口握手，只读窗口向壳要重放。
6. **iframe 里写 `one-plugin://` 原地址永远加载不出来**：wry 的改写只认 `http://one-plugin.` 前缀，而 iframe 走的是资源请求，匹配不上。窗口开着、标题正确、内容一片空白 —— 现在由壳把平台相关的基址告诉界面（`pluginPageBase`）。

**迁移影响**：`tauri.conf.json` 的 CSP 放开 `frame-src`（含 `http://one-plugin.localhost`）；`src-tauri/capabilities/default.json` 增加 `plugin-*`；`main.rs` 增加插件窗口构建与自定义协议注册；`src-tauri/src/plugin.rs` 是新文件；`core_link.rs` 增加重放缓存与 `core_replay`；前端新增 `page-bridge.ts`、`PluginWindow.svelte`，`CoreClient` 增加 `callCommand`；`Snapshot` 摘掉 `notes` / `calendarEvents`（D01 已做）。

**重新评估条件**：若某类能力确实无法在 iframe 内表达（需要本地文件读写或高性能画布），才为它开独立 webview 的口子 —— 那时要重新审视权限与生命周期，不能默默开。若自定义协议在实际中不可靠，退回受控的 `blob:` / 内联资源注入，但同样不得放开 same-origin。

## ADR-019：摘要条由宿主画，插件只提供内容与页面

**日期**：2026-10（0.2.0-dev）　**状态**：接受（代码已落地，见路线 D05）

**背景**：ADR-018 定了「插件自带页面」，但对**常驻摘要条**留了一句没定死的话：「插件正常时，摘要条的内容由插件的视图给」。D05 要真去实现，才看清这句话站不住。

**问题**：摘要条要在宠物上方**常驻**。可插件只有装上并运行着才存在，而插件不在场时它连一个字都画不出来 —— 常驻位最需要它的时候，恰恰是它不在的时候。更要命的是：宠物上方的这块界面是**始终存在**的承诺，界面上写什么，宿主就等于对用户承诺了什么。让一个可能不存在的进程来履行这个承诺，宿主就失去了对「这句话从哪来」的控制。

**选择**：**分工按「在场判断」划，而不是按「谁画」划**。宿主管两件事 —— 摘要条本身（那一行字、展开面板、四态缺席话术），以及「现在该说没连上还是该说今天的日程」；插件管两件事 —— 数据（经本体调用的端口）与点开之后的那块内容界面（自带页面）。

具体地：摘要条是**宿主**的窗口（`SummaryWindow.svelte`），它自己经本体调日历与笔记两个端口（ADR-016），自己不碰提供方，也不自己判断提供方在不在场 —— 那四态由本体裁决后经 `details.providerProblem.reason` 表达。插件自带页面只在**点开之后**登场。

**这修正了 ADR-018 的一处措辞**：那里说的「摘要条的内容由插件的视图给」在常驻位上不成立。成立的版本是「**摘要条由宿主给，摘要条点开的那个页面由插件给**」。

### 摘要条必须说清楚它凭什么这么说

一条常驻的浮条比任何一段文字都更容易骗人，因为它每天都挂在那儿。因此每一条摘要都带三样凭据：本体第几版状态（`revision`，-1 意为「还没收到过状态帧」，与「第 0 版」不是一回事）、什么时候取的、以及取的是哪个领域。

四种缺席按**链路断在哪一环**排严重程度，而不是按「用户该做什么」：本体没接上 → 没安装 → 版本对不上 → 没授权 → 没运行。版本对不上排在没运行前面，因为那时插件**在跑**、界面看起来一切正常，只是给着一份用不了的接口 —— 不说出来就会被读成「今天没日程」。

**「没取到」不许长得像「没有」**。这是整个 D05 唯一真正难的一条：取数失败时不得返回空列表（会被读成「今天没有日程」），也不得保留上一次的明细（会变成「源没连上」配着上一轮的日程）。名册一变就先把旧数据**作废**，那一小段等待期只写「正在取…」—— 说「今天没有日程」是撒谎，说旧内容是拿缓存冒充今天，两者都拒绝。`readDomain` 因此**不吞失败也不返回空列表**：调用方拿到的是 `status !== 'ready'` 加一份 `undefined` 数据。

**重新评估条件**：若某天摘要条必须展示插件特有的聚合（比如 Outlook 的「今天三场会议共 4 小时」这种本地文件实现算不出来的东西），那时可以为该领域加一个「摘要贡献」能力，由插件给一行**文本**（仍不给界面），宿主照样负责缺席话术与凭据。仍然不要把常驻位交给插件。

**验证证据**：`src/lib/summary.test.ts`（32 项，覆盖四态分流与严重程度排序、「换了新取数旧数据不留着」、「名册变了先作废」、`revision` 为 -1 时不编版本号、`todayRange` 的跨月与非本地时区、按钮可点性只看名册）、`src-tauri/src/main.rs`（`place_beside` 四个布局测试：摘要在上方、上方放不下翻到下方、多显示器不出工作区、展开高度大于收起高度）。实机验收记录在 `docs/06-roadmap.md` 的 D05 小节。

**D05 实机抓到的三个问题**（都修了，且都补了回归测试）：

1. **`withOffset` 拿 UTC 的钟面拼本地偏移**：`toISOString()` 是 UTC 的时分秒，东八区 10:00 被写成 `02:00+08:00`。于是「今天」的整段边界凭空挪了 8 小时 —— 摘要查的是凌晨到凌晨的日程。改成先把时间戳平移到本地时区再取 ISO 分量。
2. **摘要条永远停在「本体没接上」**：窗口往往比本体连上更早建起来，而取数只在挂载时触发了一次。这与 D04 插件页面的坑同源（状态要**跟着订阅**走，不能拍一次快照）。抽出 `shouldRefetch` 统一判据：第一次、本体从没接上走到接上、名册变了 —— 三者任一都要重取；状态与名册都没变时不打扰本体（否则取回时间会一直跳而数据一动没动）。
3. **取数途中到来的重取请求被静默丢弃**：`if (busy) return` 让人数被吞掉，界面上留着上一轮的数据配一句新消息。改成记下来、取完再跑一次；并且**名册一变就先作废旧数据**，不等新一轮回来。

**另一处实机约束（不是 bug，是环境）**：桌面上有置顶程序时，合成点击打不到宠物窗口，无边框置顶窗口在 Windows 上也常常拿不到键盘焦点（Tab / Enter 同样进不去）。因此摘要条与插件页面一样提供启动参数 `--open-summary` / `--expand-summary` 作为**免输入的验收路径** —— 它顺带暴露了一个真实设计点：展开与否改的是**窗口高度**，而高度只有壳知道，所以界面向壳问自己多高（`client_identity` 的 `summaryExpanded`），不再自己记一份；否则壳按参数撑高窗口后，界面还在画收起的样子，看起来就像「展开失灵了」。

**迁移影响**：前端新增 `src/lib/summary.ts`（纯模型，不 import 壳与运行时）与 `src/windows/SummaryWindow.svelte`；`CoreClient` 增加 `revision()`；`ClientIdentity` 增加 `summaryExpanded`；壳新增 `summary` 窗口、`open_summary` / `hide_summary` / `resize_summary` 三个命令与 `--open-summary` / `--expand-summary` 两个启动参数；`main.rs` 的 `place_bubble` 泛化成 `place_beside(pet, target, work, gap, prefer)`，对话条与摘要条共用（前者偏好下方、后者偏向上方）；`capabilities/default.json` 增加 `summary`。**协议版本没有升** —— 四态由本体已有的 `details.providerProblem.reason` 表达，摘要条靠调用结果分流，不需要名册新增字段。
